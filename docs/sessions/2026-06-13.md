# Session — 2026-06-13

**Focus:** Flatten the tile detail popover so it "belongs to the app"; surface the existing stat on/off settings; scope themes.

## What happened

### Flat detail card (D-015) — the main change
User wanted the tile detail popover "more flat / not rounded, like it actually
belongs to the app." Root cause: `StatTileView` used SwiftUI's native `.popover`,
which renders **system chrome** — a large "Tahoe" corner radius, translucent
vibrancy material, and an arrow — and macOS fixes that rounding/arrow (no SwiftUI
knob). So it always read as a detached OS attachment, not part of the strip.

Chose (with user) to **replace it with a self-drawn card** rather than just
recolor the system popover (a recolor leaves the big radius + arrow). Implemented:

- **`Views/StatDetailView.swift`** (new) — card content extracted from
  `StatTileView.detailPopover`, wrapped in the strip's own `Theme`: flat
  `Color.black.opacity(0.82)` fill, matching `Theme.Metrics.cornerRadius` (12pt
  continuous), **no arrow**. Reads `store.visibleStats.first { $0.kind == kind }`
  inside `body` → Observation keeps values + top-process list ticking live while
  open; tolerates the stat vanishing (e.g. battery unplugged).
- **`Panel/DetailPanelController.swift`** (new) — sibling of
  `PanelWindowController`: borderless, `.nonactivatingPanel`, floating, shadowed.
  `toggle(kind:stripFrame:anchorX:)` shows the card centered on the click just
  below the strip (flips above if it'd fall off-screen, then clamps). Size is
  measured **once per open** (`fittingSize`) so it never jitters as values tick —
  same "measure once per summon" rule as the strip.
- **`Views/StatTileView.swift`** — dropped `.popover`, `@State showingDetail`,
  the `detail`/`processSection` props, and the `detailPopover` body (≈55 lines).
  The button now just calls an `onTap` closure.
- **`Views/StatsStripView.swift`** — new `onTileTap: (StatKind) -> Void` param,
  forwarded per tile as `{ onTileTap(stat.kind) }`.
- **`Panel/PanelWindowController.swift`** — exposed `var frame: NSRect?` for the
  card to anchor against.
- **`AppDelegate.swift`** — owns `detailPanel = DetailPanelController()`;
  `toggleDetail(for:)` anchors at `NSEvent.mouseLocation.x`; on
  `onVisibilityChanged(false)` (Esc / click-away / toggle-off — all routes) it
  calls `detailPanel.hide()`, so the card always dies with the strip. Two-window
  click-away is free: the global monitor only fires for clicks outside *our app*,
  and a second non-activating panel is still our app.

Built clean (`** BUILD SUCCEEDED **`, no warnings), launched, **verified on
screen by user** — flat card matches the strip. Committed `fa5fc05`.

### Settings stat on/off — already existed
User asked for "a settings panel to check on and off what it shows." It already

drag-to-reorder, driven by `AppSettings.enabledStats` → `StatsStore.visibleStats`.
Pointed user to the gear; **user confirmed it opens and toggles work** — closes

### Themes — scoped to backlog (not built)
User wants themes "later." Confirmed scope = **full named-preset system**:
accent/load colors + background/opacity + corner-radius/density, bundled into
pickable named themes ("Default", "Mono", "Neon"…), not loose knobs. Logged in
`docs/TASKS.md` backlog. Key note: requires refactoring `Theme` from a static
enum into a persisted, selectable value both the strip and detail card read.

## Session 2 — First-run hint + signing

**Focus:** Build the one-time first-run hint (queue item #1) and stand up
per-machine code signing.

### First-run hint card
**Why:** an `LSUIElement` agent app has no Dock icon / menu-bar item (D-003), so
once the auto-summoned strip dismisses a new user has no cue for how to bring it
back. The app already auto-summons the strip once on launch (`AppDelegate`), but
never *told* the user the hotkey.

**Design — reused the detail-card pattern (D-015).** The hint is just another flat
sibling card anchored beneath the strip, so `DetailPanelController` was the
template:
- **`Panel/HintPanelController.swift`** (new) — borderless `.nonactivatingPanel`,
  floating, shadowed; `show(stripFrame:)` centers the card under the strip (flips
  above if it'd fall off-screen, then clamps). No toggle, no own dismiss control.
- **`Views/FirstRunHintView.swift`** (new) — flat `Theme` card: title + the live
  bound hotkey (`AppSettings.shared.hotKey.displayString`) in a keycap chip + a
  secondary cues line (Esc / click-away / ⚙). Copy left as a clean default —
  flagged to the user as the place to shape later.
- **`Model/AppSettings.swift`** — `hasSeenHint` persisted `Bool` (+ `Keys` entry,
  init load). Policy (user choice): **mark seen on first display** so it never
  returns; **dismiss with the strip** (rides `onVisibilityChanged`).
- **`AppDelegate.swift`** — `hintPanel`; `showFirstRunHintIfNeeded()` on first
  launch; added `hintPanel.hide()` to the existing `onVisibilityChanged(false)`
  teardown next to `detailPanel.hide()` → card dies with the strip on every hide
  path, zero new dismissal code.

**Centering bug found + fixed.** First probe showed the hint ~46px left of the
strip's center. Cause: samplers schedule `deadline: .now()` but deliver via async
`Task { @MainActor }` hops, so when `showFirstRunHintIfNeeded()` runs synchronously
at end-of-launch **no samples have landed** — the strip was measured *without* the
battery tile (`isPresent` still false), then grew ~one tile wider a beat later
(content-driven width, D-008), leaving the t=0-anchored hint off-center. Fix:
defer the hint by `asyncAfter(0.2s)` and re-read `panel.frame` so the strip has
settled. Re-probe: strip midX 994 vs hint midX 993.5 (½px), 6pt gap exact. ✅

- **`Config/Debug.local.xcconfig`** (gitignored via `**/Debug.local.xcconfig`) —
  `CODE_SIGN_STYLE = Manual`, `DEVELOPMENT_TEAM = FDMSRXXN73`,
  `CODE_SIGN_IDENTITY = Apple Development: GREGOR MÜLLER (H56HM4MMZS)`.
- **`project.yml`** — added `configFiles: { Debug: Config/Debug.xcconfig }` on the

## Session 3 — Close out queue item #1 (hint copy + persistence verification)

**Focus:** Finish the two loose ends left on the first-run hint: refine the hint
copy and settle the "slider/recorder persistence across relaunch" question.

### Persistence — confirmed by inspection (no code change)
Read the live on-disk domain: `defaults read com.sim.QuickStatsPanel` showed only
`hasSeenHint = 1` and `knownStats`. The slider/recorder keys (`interval`,
`stripHeight`, `hotKeyCode`, `anchor`, `statOrder`, `enabledStats`) were **absent**
— but that's correct **write-on-change** behavior: each is written only inside its
`didSet { defaults.set(...) }`, which fires on a *change*. On a fresh install
`init` reads them with code-level fallbacks (`interval 1.0`, `stripHeight 36`,
`hotKey .default`) and never writes them, so "no key" just means "never touched."

**The dump itself proves persistence works:** `hasSeenHint` uses the *exact same*
`didSet→defaults.set` pattern as the sliders/recorder, and it survived to disk as
`1`. The structurally-identical `interval`/`stripHeight`/`hotKey` writes persist
the same way; the only reason they're not yet on disk is they were never exercised.
Closes the "unconfirmed" flag (a live UI round-trip remains a nice-to-have, not a
risk).
