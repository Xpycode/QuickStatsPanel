## What happened

### Flat detail card (D-015) — the main change
User wanted the tile detail popover "more flat / not rounded, like it actually
belongs to the app." Root cause: `StatTileView` used SwiftUI's native `.popover`,
which renders **system chrome** — a large "Tahoe" corner radius, translucent
vibrancy material, and an arrow — and macOS fixes that rounding/arrow (no SwiftUI
knob). So it always read as a detached OS attachment, not part of the strip.

Chose (with user) to **replace it with a self-drawn card** rather than just
recolor the system popover (a recolor leaves the big radius + arrow). Implemented:

- **`Views/StatDetailView.swift`** (new) — card content extracted from
  `StatTileView.detailPopover`, wrapped in the strip's own `Theme`: flat
  `Color.black.opacity(0.82)` fill, matching `Theme.Metrics.cornerRadius` (12pt
  continuous), **no arrow**. Reads `store.visibleStats.first { $0.kind == kind }`
  inside `body` → Observation keeps values + top-process list ticking live while
  open; tolerates the stat vanishing (e.g. battery unplugged).
- **`Panel/DetailPanelController.swift`** (new) — sibling of
  `PanelWindowController`: borderless, `.nonactivatingPanel`, floating, shadowed.
  `toggle(kind:stripFrame:anchorX:)` shows the card centered on the click just
  below the strip (flips above if it'd fall off-screen, then clamps). Size is
  measured **once per open** (`fittingSize`) so it never jitters as values tick —
  same "measure once per summon" rule as the strip.
- **`Views/StatTileView.swift`** — dropped `.popover`, `@State showingDetail`,
  the `detail`/`processSection` props, and the `detailPopover` body (≈55 lines).
  The button now just calls an `onTap` closure.
- **`Views/StatsStripView.swift`** — new `onTileTap: (StatKind) -> Void` param,
  forwarded per tile as `{ onTileTap(stat.kind) }`.
- **`Panel/PanelWindowController.swift`** — exposed `var frame: NSRect?` for the
  card to anchor against.
- **`AppDelegate.swift`** — owns `detailPanel = DetailPanelController()`;
  `toggleDetail(for:)` anchors at `NSEvent.mouseLocation.x`; on
  `onVisibilityChanged(false)` (Esc / click-away / toggle-off — all routes) it
  calls `detailPanel.hide()`, so the card always dies with the strip. Two-window
  click-away is free: the global monitor only fires for clicks outside *our app*,
  and a second non-activating panel is still our app.

Built clean (`** BUILD SUCCEEDED **`, no warnings), launched, **verified on
screen by user** — flat card matches the strip. Committed `fa5fc05`.

### Persistence — confirmed by inspection (no code change)
Read the live on-disk domain: `defaults read com.sim.QuickStatsPanel` showed only
`hasSeenHint = 1` and `knownStats`. The slider/recorder keys (`interval`,
`stripHeight`, `hotKeyCode`, `anchor`, `statOrder`, `enabledStats`) were **absent**
— but that's correct **write-on-change** behavior: each is written only inside its
`didSet { defaults.set(...) }`, which fires on a *change*. On a fresh install

`hotKey .default`) and never writes them, so "no key" just means "never touched."

**The dump itself proves persistence works:** `hasSeenHint` uses the *exact same*
`didSet→defaults.set` pattern as the sliders/recorder, and it survived to disk as
`1`. The structurally-identical `interval`/`stripHeight`/`hotKey` writes persist
the same way; the only reason they're not yet on disk is they were never exercised.
Closes the "unconfirmed" flag (a live UI round-trip remains a nice-to-have, not a
risk).

## Session 4 — ⌘, opens Settings

**Focus:** Add the macOS-standard ⌘, Settings shortcut.

**Why it's not a one-liner:** no menu bar (LSUIElement, D-003) to host a
"Settings…" item, and the panel is `.nonactivating` so it never becomes key — a
SwiftUI `.keyboardShortcut` on the strip would never receive the keystroke (the
same wall that forced the hotkey recorder into the separate Settings window). The
only mechanism that fits is the **scoped Carbon hotkey** pattern Esc already uses
(D-010): permission-free, fires regardless of focus, registered only while the
panel is visible.

**Change (mirrors `dismissHotKey`):**
- `HotKeyService.swift` — new `.commaSettings` binding (`kVK_ANSI_Comma` + `cmdKey`).
- `AppDelegate.swift` — `settingsHotKey = HotKeyService(id: 3)`; register
  (`→ openSettings()`) / unregister inside the existing `onVisibilityChanged`
  closure next to Esc; `unregister()` in `applicationWillTerminate`.
- `StatsStripView.swift` — gear tooltip `"Settings"` → `"Settings (⌘,)"`.

**Trade-off (accepted, same as Esc):** while the panel is on screen ⌘, is captured
globally, so it opens *our* Settings even if another app is frontmost — but the
user just summoned the HUD, so that's the intent; it reverts the instant the panel
hides. Clean signed build; **user confirmed ⌘, opens Settings on screen.**

## Session 5 — Themes: spec → plan → Wave 1 (research-driven)

**Focus:** Kick off the Themes (named presets) feature properly: research-backed
`/spec`, a wave-based `/plan`, and execute Wave 1. Drove the whole thing with
parallel research agents + Apple MCPs + web (user asked for "agents, mcps and the web").

### Research (3 parallel agents)
1. **Apple HIG** (HIG/docs MCP) — appearance, color semantics, density, translucency.
2. **SwiftUI theming architecture** (Apple docs/WWDC + context7) — Observation across
   multiple `NSHostingView` roots.
3. **Competitor teardown** (web) — iStat Menus, Stats/exelban, iGlance, MenuMeters.

**Decisive findings:**
- **Singleton, not `@Environment`.** The 3 panels (strip/detail/hint) are separate
  `NSHostingView` roots with no shared SwiftUI scene; `@Environment` isn't shared across
  them (would need per-root injection + re-injection, easy to leave a stale panel).
  SwiftUI Observation tracks a global/singleton when read in `body` — and the views
  already read `AppSettings.shared` directly — so the theme rides the existing singleton.
- **One status function.** Stats/exelban models color as `usageColor(zones:reversed:)`;
  a `reversed` flag covers battery ("low = hot") and deletes our `100 - percent` hack.
- **Named curated presets are a differentiator** — every competitor ships loose per-module
  knobs, nobody ships "Default/Mono/Neon"-style bundles.
- **HIG constraints → acceptance criteria:** no manual per-app light/dark toggle; status
  color never the sole cue; honor Reduce Transparency / Increase Contrast; text ≥10pt /
  controls ≥20×20pt; high-translucency needs a dimming floor.

### Spec — `specs/themes.md` (new, finalized)
11 ACs (Given/When/Then), locked architecture sketch (`ThemePreset` enum + `Theme` token
struct + `AppSettings.theme`), technical considerations, out-of-scope, research provenance.
**User decisions captured** (via AskUserQuestion):
- Appearance: **follow system light+dark** (no manual toggle).
- Scope: **presets + custom knobs**.
- Presets: **Default, Mono, Vitals, Neon** (+ Custom).
- Bands: **unified `usageColor(zones:reversed:)` + hysteresis**.
- Open-Q resolutions: **flat fill + manual reduce-transparency fallback** (not Material);
  **density = font/spacing/radius only**, `stripHeight` stays sole height source; **Default =
  today's exact dark tokens verbatim** (seamless upgrade for dark users); **accent follows
  system** (`Color.accentColor`). Two open Qs deferred to build (hysteresis margin/state
  location; concrete non-color severity cue) — both have documented "leans".

### Plan — `IMPLEMENTATION_PLAN.md` (new)
12 atomic tasks / 5 waves. Shape is dictated by **one chokepoint** (Wave 2 = `Theme`
static→struct + `AppSettings` wiring); small parallel foundation before it, wide parallel
view-migration after it. A transitional `enum Theme` **facade** (forwards to
`AppSettings.shared.theme`) lets Wave 2 build clean before any view is touched — turns a
flag-day rewrite into always-green steps. Status color resolved **in the store** (descriptor
carries `tint`) so hysteresis's per-`StatKind` "last band" state lives in one place, not a
stateless `body`. TASKS.md Current Sprint synced (W1–W5).
